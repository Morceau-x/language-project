# Step 2 — Compiler layers and tooling

Step 1's compiler had three layers: lexer, parser, code generator. Real
compilers have many more, and they're built with tools: parser
generators, intermediate representations, optimizers, LLVM. In this
step Mini keeps its tiny arithmetic language (plus inputs) and grows the
inside of a real compiler, one layer at a time:

```text
x * (2 + 3) + y * 0                       mini/programs/inputs.mini
```

```text
fn main(%x, %y) {                         your IR, after your optimizer
  %1 = mul %x, 5
  ret %1
}
```

```text
mini_main:                                x86-64, from LLVM
	leaq	(%rdi,%rdi,4), %rax                   x + 4·x, in one instruction
	retq
```

```bash
$ ./inputs 4 100
20
```

and skim [the Rust you need](rust-concepts.md) for this step. Expect
8–12 hours: each part below is a session or two.

## The big picture

### The language

Mini gains one thing: **names**. A name is an *input* of the program,
given on the command line when it runs.

```text
program = expr EOF ;
expr    = term { ( "+" | "-" ) term } ;
term    = unary { ( "*" | "/" ) unary } ;
unary   = "-" unary | primary ;
primary = INT | IDENT | "(" expr ")" ;
IDENT   = letter or "_", then letters, digits or "_"
```

```bash
$ cargo mini run mini/programs/division.mini 10 3       # total / count
3
```

Why inputs? Without them, every program is a constant: the optimizer
would turn all of them into `ret 7`, and there would be nothing left to
learn from it. With inputs, the compiler can't know the answer, only
make the computation cheaper.

### The meaning

A compiler with an optimizer and three ways to run a program needs a
precise definition of what each program computes, or the ways will
disagree. Here is Mini's:

- Values are 64-bit signed integers.
- The inputs come in the order their names **first appear** in the
  program: in `total / count`, `total` is the first input.
- `+`, `-`, `*` and negation **wrap around** on overflow (two's
  complement): `9223372036854775807 + 1` is `-9223372036854775808`.
  That's what Java and Go do, and what LLVM's plain `add` does.
- `/` rounds toward zero: `-7 / 2` is `-3`. The one overflowing
  division, `-9223372036854775808 / -1`, wraps to itself.
- **Division by zero is a runtime error**: the program prints
  `error: division by zero` and exits with status 1.

Step 1 said "like Rust's `i64`". That was vague: Rust panics on
overflow in debug builds and wraps in release builds. A language must
pick one.

### The layers

```text
                    hand-written (step 1, Part 1)
               ┌──▶ lexer ──▶ tokens ──▶ recursive descent parser ──────────┐
 source text ──┤                                                           ├──▶ AST
               └──▶ lexer ──▶ lexemes ──▶ LR parser ──▶ CST ──▶ prune ──────┘
                    generated by grmtools (Parts 2, 3, 4)                    │
                                                                        lower (Part 5)
                                                                             ▼
                                IR ──▶ fold, cse, dce (Part 6) ──▶ optimized IR
                                                                             │
                     ┌──────────────────────────┬────────────────────────────┤
                     ▼                          ▼                            ▼
              interpreter (5)           JavaScript (7)                 LLVM IR (7)
                     │                          │                            │ clang + runtime
                   result                    Node.js                 native executable
```

| Part | You build                               | Compiler ideas                                                                      | Files                                |
|------|-----------------------------------------|-------------------------------------------------------------------------------------|--------------------------------------|
| 1    | inputs in the hand-written front end    | tokens that borrow, trees that own                                                  | `lexer.rs`, `ast.rs`, `parser.rs`    |
| 2    | a C calculator, generated by Bison      | LR parsing, shift and reduce, the automaton, conflicts, precedence declarations     | `bison/calc.y`                       |
| 3    | a second front end, generated in Rust   | parser generators, build scripts, generated code, error recovery                    | `yacc/mini.l`, `yacc/mini.y`         |
| 4    | parse tree → AST                        | concrete vs abstract syntax, lossless trees, differential testing                   | `prune.rs`                           |
| 5    | AST → IR, and an IR interpreter         | three-address code, SSA, lowering, a reference semantics                            | `ir.rs`, `lower.rs`, `interp.rs`     |
| 6    | an optimizer                            | passes, "replace all uses", fixpoints, what may and may not be removed, fuzzing     | `opt/`                               |
| 7    | JavaScript and LLVM backends            | LLVM IR, undefined behaviour, name mangling, a runtime library, linking             | `backend/`, `runtime/mini_rt.c`      |
| 8    | nothing new: you look inside            | LLVM's optimizer and code generator, assembly, `--emit` for every layer             |                                      |

### Best practices this step adds

| Practice                                             | Why                                                                                               | Where                              |
|------------------------------------------------------|---------------------------------------------------------------------------------------------------|------------------------------------|
| **One IR between front ends and back ends**          | 2 front ends × 3 back ends need 2 + 3 translations, not 2 × 3; optimizations are written once     | `ir.rs`                            |
| **The semantics lives in one function**              | the interpreter and the constant folder both call `eval_binary`, so they can't disagree           | `ir.rs`                            |
| **Small passes that each do one job**                | each is easy to test alone; a pass manager combines them                                          | `opt/`                             |
| **Every layer can be printed**                       | `mini --emit=ir` is to Mini what `rustc --emit=mir` or `clang -emit-llvm` are to them             | `driver.rs`, `main.rs`             |
| **Differential testing**                             | two parsers must build the same tree; three back ends must print the same answers                 | `tests/end_to_end.rs`              |
| **Property-based testing**                           | hundreds of random programs find the cases you didn't think of, then shrink them                  | `tests/properties.rs`              |
| **Generated code is never edited by hand**           | the grammar is the source of truth; `build.rs` regenerates the parser on every build              | `build.rs`                         |
| **A runtime library for what isn't compiled**        | reading inputs and printing results is the same for every program: write it once, in C            | `runtime/mini_rt.c`                |

## How to work through this step

The same rhythm as step 1: **read the test, write the code, run the
test.** Each task is a `todo!()` with its tests, folded hints and a
folded solution. Part 2 is different: you work in C with Bison, and run
commands instead of tests.

Do the parts in order: each one uses the ones before it. Within a part,
the tasks are ordered so that each one's tests only need the ones
before.

Run the tests of one task with a filter, for example:

```bash
cargo test -p mini --lib lexer
```

`--lib` runs only the unit tests, the ones inside `src/`. The
integration tests in `tests/` exercise the whole compiler, so they only
pass at the end of Part 7; the guide tells you when to run which.

`cargo test -p mini` stops at the first test *file* that has a failure,
so the integration tests in `tests/` only run once the unit tests all
pass. To see everything at once:

```bash
cargo test -p mini --no-fail-fast
```

### The first build

```bash
cargo test -p mini --no-fail-fast
```

The first build takes a minute: Mini now has dependencies (see below).
You should see **45 passed, 83 failed**. The passing ones are step 1's
tests, which your code from step 1 still passes. The failures say
`not yet implemented: Part 5a: Function::show` and the like, or show an
expected and an actual value.

### The `mini` command

The compiler you're building is a program called `mini`. To run it,
use `cargo mini`, a shortcut defined in `.cargo/config.toml` at the
workspace root: it rebuilds `mini` if its code changed, then runs it
with your arguments. (It's short for `cargo run -q -p mini --`.)

```bash
cargo mini --help
```

```text
usage: mini [OPTIONS] FILE.mini                 compile to JavaScript (or --emit another layer)
       mini run [OPTIONS] FILE.mini [INPUT...]  run the program with the IR interpreter
       mini build [OPTIONS] FILE.mini           build a native executable with clang

options:
  --emit=LAYER        print one layer: tokens, cst, ast, ir, js (the default) or llvm
  -O                  optimize the IR
  --print-after-each  print the IR after each optimization pass that changed it (to stderr)
  --parser=yacc       parse with the generated parser instead of the hand-written one
  -o OUTPUT           where `mini build` writes the executable (default: FILE without .mini)
```

Each layer starts working when you finish its part. Right now, only
step 1's layers work, and only on programs without names:

```bash
cargo mini --emit=tokens mini/programs/arithmetic.mini
```

```bash
cargo mini --emit=ast mini/programs/arithmetic.mini
```

Run these from the workspace root, the folder with the top-level
`Cargo.toml`: the file paths in the guide start from there. (If you'd
rather type `mini`, add `alias mini='cargo mini'` to your `~/.zshrc`.)

### About the `#![allow(...)]` line in `lib.rs`

Still there, for the same reason as in step 1: code that a `todo!()`
will use looks unused. You delete it in Part 8.

### About `tests/properties.proptest-regressions`

When a property test fails, proptest saves the failing case in this
file, to try it first next time (Part 6 explains why). While parts are
unfinished, property tests fail on `todo!()`, so the file appears.
Delete it whenever you like.
